# 精算の数え方（店ごとの設定）

管理画面「精算 › 精算の数え方」（`/app/settlement-calc-settings`）で選ぶ。保存先は AppSetting `settlement_calc_settings`（`app/utils/settlementCalcSettings.ts`）。**初めの値は今の数え方のまま**で、保存していない店の精算・売上サマリーは変わらない。

POS Receipt は販売するアプリなので、特定の店（Ciara）の運用はコードに店の名前を書かず、この設定で選ぶ（T さん 2026-11-22）。ciara-system の精算（`lib/sales/settlement-receipt/`、GAS 精算レシートの移植）と同じ数え方にしたい店の選び方も下に書く。

| 設定 | 初めの値（今の動き） | ciara-system と同じにするとき | 使う所 |
|---|---|---|---|
| 売上を数える日 | 決済した日（SALE / CAPTURE の時刻） | 注文の日（`processedAt`）。決済が確定していない注文はオーソリを売上に数える（成功したオーソリだけ。失敗・VOID したものは数えない） | `aggregateGasStyleForOrders` |
| 点数に数えない商品 | なし | ノベルティの SKU を入れる。0 円の明細だけ外し、返品の点数でも外す | 同上 |
| 返金の支払方法の付け替え | なし | 例: 店＝梅田エスト店・天王寺ミオ店、支払方法に含まれる文字＝wespo、付け替え先＝現金 | 同上（REFUND の取引だけ） |
| ギフトカードの返金 | OFF | ON（付け替え先は 現金）。ギフトカードのメモの `REFUND_CASH` / `REFUND_GC` と `LOC:店の名前` で見分ける | `settlementGiftCardRefunds.server.ts` |
| 支払方法ごとの取引件数 | 売上の取引の件数 | 売上の取引の件数から返金の件数を引く | `payBucketsToPaymentSections` |
| 返金が売上より多い日 | 合計を 0 にする | 外す（合計・純売上・税をマイナスのまま出す） | `buildSettlementPreviewImpl` |
| 支払方法の分け方 | 決まった分け方（`gasNormalizeGatewayLabel`。gateway の名前から 現金・クレジットカード・電子マネー・交通系 IC・商品券などに分ける） | どちらでもよい（ciara-system は GAS と同じ決まった分け方） | `aggregateGasStyleForOrders`（`paymentKey`）・`payBucketsToPaymentSections`・特殊返金の上乗せ |

- ギフトカードの返金: 前後 2 日に作ったカードを読み、メモの日付（無ければ作った日）がその日のものを数える。日付だけのメモは店のタイムゾーンの暦日で比べる。店の名前は、精算の店の名前・ロケーションの名前・表示名・短縮名のどれかと同じなら数える（全角・半角と空白の違いは同じとみなす）。1 枚を返金 1 件として数える。Shopify から読めなかったときは 0 円にせずエラーにする（精算を確定しない）。
- ギフトカードの返金と精算設定の「旧ギフトカード API 集計」（発行額を売上に足す）は、同じカードを売上と返金の両方に数えてしまうので、旧集計が ON のあいだはギフトカードの返金を ON に保存できない。あとから精算設定で旧集計を ON にした店は、精算の計算の側でギフトカードの返金を数えない（旧集計だけが効く）。
- 無効にした（deactivate した）ギフトカードも、返金として払い出した事実は変わらないので数える（`deactivatedAt` は見ない）。ciara-system が無効のカードを外しているかは**未確認**。並行運用で差が出たら見直す。
- 「注文の日」でオーソリを売上に数えるのは、`status` が SUCCESS で、成功した VOID に取り消されていないものだけ。SALE / CAPTURE の `status` は前から見ていない（決済した日でも同じ。直すときは両方の数え方を一緒に直す）。
- 返金の計上ロケーション（注文基準／返金トランザクション基準、POS 以外の返金の計上先）は、前から精算設定とロケーションで選べる。ciara-system は Flow が注文に書く `pos.refund_aggregation_location` で決める。注文の記録を読む直しは PR #11。
- 税率は前から精算設定で選べる（初めは 10%）。精算設定の「税丸め」は保存できるが、精算の計算には使っていない（今は四捨五入だけ）。
- 数え方を変えると、売上サマリー（精算プレビューを読む）の数字も同じに変わる。すでに確定した精算は作り直すまで変わらない。
- 支払方法の分け方（`paymentKeySource`）: 「支払方法マスタで分ける」を選ぶと、取引の gateway が `rawGatewayPattern` に（または formattedGateway が `formattedGatewayPattern` に）当たる最初のマスタ（並び順）の**表示名**を精算の行の名前（集計キー）にする（`app/services/paymentKeyMasterPure.server.ts`）。どのマスタにも当たらない取引は決まった分け方の行に入れる（売上・返金を落とさない）。現金の上限（おつりを売上に入れない）は種類が「現金」のマスタの行に、商品券のおつりの観測は「商品券として扱う」か種類が「商品券」のマスタの行に効く。種類が「未分類」のマスタは決まった分け方の判定を引き継ぐ。現金の種類の行が 2 つ以上ある注文は、上限で削る額を並んだ順に削る。返金の付け替え・ギフトカードの返金の「支払方法の名前」は、この行の名前に当てる。特殊返金の手段（マスタの gateway の名前）も同じ resolver で行の名前に直してから探す。画面には、切り替えると行の名前が変わるマスタ（登録した gateway の名前で見た目安）を出す。確定済みの精算は変わらない。
- 「支払方法の分け方」を途中で変えると、変えた日の前後で支払方法の行の名前が変わる（確定済みの日は前の名前のまま）。照合用 CSV や ciara-system との比べで同じ支払方法が 2 つの名前に分かれるので、切り替えは月の始めにする。マスタで分ける店では、返金の付け替え先（`toLabel`）をマスタの表示名にする（違うと画面に注意が出る）。
