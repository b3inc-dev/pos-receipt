## この文書の使い方

Shopify POS の UI 拡張（タイル・注文の詳細の行・会計後のブロック）で画面を作るときは、この文書のルールに従います。pos-receipt で T さんが実機（iPhone の POS）で確かめながら決めたことを、ほかの POS アプリでも使える形にしたものです。

- 読み手: ほかのプロジェクトで POS 画面を作る人と Claude。
- 強さ: 「〜する」「〜しない」は守るルール。違う作りにしたいときは、先に T さんに確認する。
- 実例: 各ルールの下の「pos-receipt では」は、そのルールが実際にどう入っているかの例です。ファイル名は pos-receipt リポジトリの `extensions/` からの場所です。
- 正: この文書と実装が食い違うときは、実機で確かめた実装を正とし、この文書を直します（最後の「出典と実装との差」に食い違いを書いています）。
- 管理画面のルールは別の文書「管理画面の UI ルール（完全版 v1.1）」（[`docs/UI_RULES.md`](UI_RULES.md)）が正本です。ここでは POS だけを扱います。

## 1. 画面の骨組み

どの画面も「上に見出しと条件、真ん中に中身、下に固定のボタン」の3段で作ります。店の人がどの画面でも同じ指の動きで使えるようにするためです。

### 下の固定フッター

- 画面の一番下に固定の帯を置き、左下に「戻る」、右下にその画面の主なボタンを1つだけ置く。スクロールしても動かない。
- 前の画面へ戻るボタンは必ず「戻る」。「← 戻る」「注文一覧に戻る」のようにしない。スクロールの一番下にも置かない。
- 一覧の「登録」「履歴」などの操作も、一覧の上ではなくフッターの右下に置く。
- 別の画面を開くボタン（戻るのではないもの）は「戻る」と書かず、開く先の名前にする。

pos-receipt では: フッターは共通部品 `pos-smart-grid/src/FixedFooterNavBar.jsx`（POS Stock と同じ作り）。注文一覧は右下に「会計前に登録」（商品券）「返金前に登録」（返金の予約が有効なときだけ）、領収書の一覧は右下に「履歴」。精算の左下「履歴一覧」は履歴を「開く」ボタンなので「戻る」にしていない。

### 上の固定

- 一覧画面は、検索・日付・状態の絞り込み・「店名・HH:MM に更新」までを上に固定し、その下に区切り線と少しの余白を入れてから行を並べる。
- 区切り線は `s-divider` で引く（POS の `s-box` には枠線の指定が無い）。

### 見出しとボタンは入口ごとに1つ

- 注文の詳細のように複数の入口（タイル）から開く画面は、その入口に合った見出しを1つと、右下のボタンを1つだけ出す。別の機能の見出しやボタンを混ぜない。
- 画面のタイトルは「何をする画面か」を言う（例:「現金を直す」「商品券釣銭を登録」）。

pos-receipt では: 同じ注文でも、「返金方法変更」タイルから開くと見出し「返金方法変更」＋右下「返金方法を変更」、「商品券釣銭登録」タイルから開くと見出し「商品券釣銭登録」＋右下「商品券釣銭を登録」だけが出る。入力画面のタイトルは `${返金方法}を直す`。

### 入力画面・確認画面の見た目

入力と確認の画面は、注文の詳細と同じ見た目にそろえます。

- 区切りは灰色の小さい見出し（`s-text type="small" color="subdued"`）。枠で囲まない。
- 1行は「左に項目名、右に値」。マイナスの金額は赤で「−¥1,100」。
- 確かめるべき金額（変更後の金額、釣銭など）は `s-heading` で大きく出す。
- 変える画面では「変更前」と「変更後」を並べて見せる。

pos-receipt では: 部品は `pos-smart-grid/src/AdjustFormParts.jsx`（FormHeading・FormLine・FormHero）、注文の詳細は `OrderDetailSummary.jsx` と `common/orderDetailLayout.js`。画面イメージはプロジェクトの `mockups/refund-voucher-screens.html`。

### 完了画面

- 完了画面も固定フッターにする。左下に「閉じる」、右下に次の主な操作（例:「再印刷」）を 1 つ。
- 流れは「入力 → 確認 1 回 → 完了」。確認を 2 回に分けない（3章）。

pos-receipt では: 領収書は「領収書情報を入力 → 確認 → 発行完了」、精算も確認・完了を同じ形にそろえている。

## 2. 一覧画面

一覧は POS 純正の「すべての注文」に見た目を合わせます。T さんが実機で「一覧関係はこれで行こう」と決めた形で、ほかの一覧（履歴など）もこの形にします。

上から順に次のように並べます。

1. 検索欄
2. 日付の行: 左に「年」「月」「日」のボタン、右端に「今日」。開いたときは今日。
3. 状態の絞り込み: 開いたまま常に見せ、幅いっぱいを等分して並べる。選んだものは primary、ほかは secondary。
4. 「店名・HH:MM に更新」
5. 区切り線（`s-divider`）と少しの余白
6. 行（スクロールするのはここだけ）
7. 下の固定フッター: 左「戻る」、右に登録や履歴

細かい決まり:

- 絞り込みのボタン名は iPhone でも 1 行に収まる短さにする（例:「返金」）。
- 絞り込みで 0 件になったときは「今日の取引は 12 件ありますが、返金の取引はありません。」のように全体の件数を言い、「すべて表示する」ボタンを置く。
- バッジは状態ごとに色を分ける（例: 一部返金 = caution、返金済 = warning）。バッジの文字に空白を入れない（「商品券登録済」）。
- バッジと履歴の操作は入口（タイル）ごとに分ける。そのタイルと関係のない種類の行は、読むだけにして注記を添える。
- さらにあるときは行の下に「さらに読み込む」。
- 一覧は今いる店と選んだ日だけを出す。日付は店の時間帯（日本の店は JST）で数える。

純正と変えている所（POS UI 拡張に同じ部品が無いため）: 検索欄のバーコード読み取りが無い。絞り込みは開いたまま並べる。日付は年・月・日のボタンで選ぶ。

pos-receipt では: `pos-smart-grid/src/OrderDayListScreen.jsx`（領収書・販売レシート・返金・商品券で共有）と行の `OrderListRow.jsx`、文言は `common/orderListLabels.js`。等分は `s-stack direction="inline" gap="none" inlineSize="100%"` の中に幅 N% の `s-box` を並べ、その中に `s-button` を入れる（`s-button` には幅の指定が無いため。POS Stock の「未入庫／入庫済み」と同じ作り）。

## 3. 確認と結果の出し方

取り消せない処理やお金が動く処理は、押す前に確認を出します。確認は短く、何が起きるかだけを言います。

| 場所 | 決まり | 例 |
| --- | --- | --- |
| タイトル | 処理の名前。「確かめ」「確認」だけにしない | 「カートに入れる」「下書き注文を作成」「精算の発行」 |
| 本文 | 1文で、何がどうなるか。金額や点数を入れる | 「#1234 と同じ商品 3 点をカートに入れます。」 |
| 実行ボタン | 動詞。「OK」「はい」にしない | 「入れる」「作成する」「登録する」 |
| 取り消しボタン | 「やめる」 | 「やめる」 |
| 結果 | 押したボタンの近くに出す。画面の上に離して出さない | 「カートに入れました（3 品目）」 |

- 補足は本文の下に灰色の小さい字で1行まで（例:「元の注文の返金・キャンセルはそのままです。」）。
- 押してから結果が出るまで、そのボタンを処理中（`loading`）にして二度押しを防ぐ。
- 失敗の文は理由が分かる日本語にする。英語のエラーや「(HTTP 500)」はそのまま出さず、決まった日本語（「注文を読み込めませんでした。少し待ってから、もう一度…」）に置き換える。
- ブラウザの `confirm()` は使わない。
- 確認は 1 回にまとめる。内容の確認と実行の確認を別々に出さない。

確認をどこに出すか（実装で分かったこと）:

- 重ね表示の `s-modal` は、端末によっては見出しだけ変わって確認が出ないように見えた。精算の発行確認は「画面ごと切り替える」形にした。
- 注文の詳細の中の操作（会計をやり直す）は、その欄の中に確認・途中・結果を同じ形で出す。
- `s-modal` を使うときは、画面に常に置いておき、ボタンの `command="--show"` と `commandFor={id}` で開く（`showOverlay` だけだと開かないことがある）。

pos-receipt では: `pos-smart-grid/src/RedoCheckoutSection.jsx`（会計をやり直す）、`SettlementModal.jsx` の発行確認画面、共通のエラー文は `common/errorMessage.js`。

## 4. 読み込みと更新時刻

読み込み中の表示は、見出しのすぐ下の青い帯1つだけにします。画面が固まったように見せず、表示も入れ替えません。

- 文は「読み込み中です。少しお待ちください。」。`s-banner tone="info"` の `heading` に入れる（端末によって本文が畳まれるため）。
- 画面の枠（見出し・日付・下のボタン）は先に出し、まだ押せないボタンは `disabled` で薄くする。
- 読み込みの途中で、別の文や別の形の表示に切り替えない。
- 失敗は同じ場所に赤い帯（`tone="critical"`）で、理由と次にすることを1文で。
- 「再読み込み」ボタンは、失敗したときか、待ちが長いとき（10 秒ほど）だけ出す。幅の広いボタンは「再読み込み」、小さいボタンは「再読込」。「読み込み直す」とは書かない。
- 集計を最新にするボタン（精算・売上サマリー）は「更新」のままでよい。「再読み込み」は失敗後にやり直すボタンだけの名前。

更新時刻と日時:

- 取り直した時刻は「HH:MM 更新」の書き方で出す。一覧では店名を前に付ける。
- 日時は日本時間（JST）で出す。端末の時間帯や UTC に任せない。日付は「2026/11/24」のようにスラッシュで、API や内部の値は `YYYY-MM-DD` のまま。

pos-receipt では: 帯は `SettlementModal.jsx` の `SettlementTopNotices`、時刻は `common/dateDisplay.js` の `formatJstHm`（Intl の時間帯に頼らず UTC+9 で計算）と `formatYmdSlash`。

画面の中の一部だけ（値 1 つ、選ぶ欄の中身など）が待ちのときは、その場所に前置きなしの「読み込み中…」だけを出す。「支払方法を読み込み中…」のように何を読んでいるかは書かない。

pos-receipt では: 全画面共通の `pos-smart-grid/src/LoadingNotice.jsx`（文と 10 秒の待ちは `common/loadingNotice.js`）。段階的に読む画面でも、待っている読み込みをまとめた真偽値を 1 つ渡し、帯を 1 つのまま出し続ける。

## 5. 入力

店の人には、アプリが知らないことだけを入れてもらいます。分かっている金額は画面に見せ、打たせません。

### 金額

- 分かっている金額は入力させない。入力欄は、本当に入れる必要があるときだけ出す。
- 判断に要る金額（注文の合計、支払方法ごとの支払い済み・返金済み）は、入力欄の近くに必ず見せる。
- 計算で決まる値（例: 釣銭 = 額面 − 商品券で払った額）は自動で出し、大きく見せる。
- 式を項目名に書くと、店の人が値を確かめやすい（「釣銭（額面 − 商品券で払った額）」）。

### 候補ボタン

- 候補ボタンは、実際に選ばれる意味のある値だけにする。意味のないボタン（どの注文でも同じ金額、選ぶと変な結果になるもの）は置かない。
- 例（商品券の額面）: 払った額より上の近い 100 円区切り 1 つと、その次の 500 円区切り 2 つ。¥2,230 → 2,300 / 2,500 / 3,000。¥2,430 のように 100 円区切りが 500 の倍数と重なるときは 2,500 / 3,000 / 3,500。
- 「全額反映」のようなボタンも、意味がある画面だけに置く。商品券の額面では全額を入れると釣銭が 0 になるので、置かない。返金の金額では、支払方法の行ごとに「全額反映」を置く。

### 選ぶ欄と状態

- 選ぶ欄は `s-choice-list`、オン・オフも `s-choice-list` で作る（7章: POS に `s-select` / `s-checkbox` は無い）。
- 登録済みでもう一度登録できないものは、ボタンを押せない状態（`disabled`）にし、なぜ押せないかを1文で出す。直す入口があるときはその場所を言う（「直すときは、調整履歴の「変更」を押してください。」）。
- その注文では使えない機能は、入力画面を開かずに理由を出す（「この会計は商品券釣有りではないので、商品券釣銭は登録できません。」）。

pos-receipt では: 候補は `common/voucherFaceCandidates.js`（試験つき）と `pos-smart-grid/src/VoucherFaceCandidates.jsx`、元の支払いと「全額反映」は `SpecialRefundModal.jsx` の `OrderTenderPanel`、選ぶ欄は `PosChoiceField.jsx`。

## 6. 文言

画面の文は、店の人がそのまま読める平易な運用の日本語にします。同じものは全画面で同じ言葉で呼びます。

- 生のキー（`cash_refund` など）、英語、開発者向けの言葉（「Printing API で印字」「接続先」「認証」など）を画面に出さない。内部の値は必ず日本語の名前に直して出す。
- 用語は1つに決め、全画面でそろえる。言い換えを混ぜない。
- タイル名は「機能名」＋小見出し「できること」で短く。タイル名と小見出しで同じ言葉を繰り返さない。
- 画面タイトルは何をする画面かを言う（「〜を直す」「〜を登録」）。
- 拡張名（`shopify.extension.toml` の name）も店の人が見る文字。purchase.post の行は POS が拡張名で描くので、画面と同じ用語にする。
- 記録 ID・発行 ID などの内部の ID は画面に出さない。店の人が探すときは注文番号・日時・金額で探す。
- Shopify の「ロケーション」は、店の人には「店舗」と書く。

pos-receipt で決めた用語（ほかのアプリでも同じ意味ならこれを使う）:

| 使う言葉 | 使わない言葉 | メモ |
| --- | --- | --- |
| 釣銭 | 釣り | 「商品券釣有り」は支払方法マスタの名前なのでそのまま |
| 返金方法 | 返金手段 |  |
| 変更 | 付け替え | 「返金方法変更」 |
| 登録 | 調整 | 店の人が入れる操作は「登録」（「商品券釣銭登録」）。登録の一覧は「調整履歴」のまま |
| 再読み込み（小さいボタンは再読込） | 読み込み直す | 失敗後にやり直すボタンだけ |
| 戻る | ← 戻る、注文一覧に戻る | 左下固定 |
| やめる | キャンセル、いいえ | 確認の取り消し |

タイルの例:

| タイル名 | 小見出し |
| --- | --- |
| 返金方法変更 | 登録・履歴 |
| 商品券釣銭登録 | 入力・履歴（会計前に額面を入れたときは「額面 5,000円 入力済み」） |
| 精算 | 精算・点検 |
| 領収書 | 発行・履歴 |

管理画面の注文ブロックの名前も同じ用語で「返金方法変更・商品券釣銭登録」です。用語を変えるときは、POS・管理画面・拡張名を一度に直します。

## 7. POS UI 拡張の制約（実機で分かったこと）

POS に無い部品や属性は、エラーも出ずに無視されます。管理画面（Polaris）と同じつもりで書くと、画面が空いたり見た目が変わらなかったりします。@shopify/ui-extensions 2025.10.x で確かめた内容です。

| やりたいこと | POS で起きること | 代わりの作り方 |
| --- | --- | --- |
| 選ぶ欄（`s-select` / `s-option`） | 何も描かれず、初めの値のまま登録される | `s-choice-list` ＋ `s-choice`、またはボタン＋一覧 |
| チェックボックス（`s-checkbox`） | 何も描かれない | 選択肢 1 つの `s-choice-list` |
| 文字の太さ・大きさ（`fontWeight` / `size` / `fontSize`） | 無視され、全部同じ大きさ | `s-text` の `type`（small / strong など）・`color`・`tone`、大きい字は `s-heading` |
| ボタンの種類（`kind`） | 無視され、選んだ状態が見えない | `variant`（primary / secondary） |
| ボタンの幅 | 指定が無い | 幅を割った `s-box` に入れる |
| 枠線・角丸・背景（`s-box` の border など） | 指定が無い | 区切りは `s-divider`、まとまりは `s-section` |
| 進み具合のバー | 部品が無い | 数字とバッジで出す |
| ブラウザの `confirm()` | 動くか確かめられていない | 3章の確認画面 |

POS の動き:

- 会計後の画面（`pos.purchase.post.*`）の「管理」の行は、POS が拡張名で描く。押すと `action.render` が直接開き、menu-item の `onClick` は呼ばれない。注文は `action.render` の中で `shopify.order.id` を読む。
- POS は古い拡張名を覚えていることがある。拡張名を変えて出し直したら、タイルを外して足し直すよう店に伝える。
- 会計後のブロック・行は、店ごとに管理画面の「販売チャネル → Point of Sale → アプリ」で有効にしないと出ない。導入手順に入れる。
- `pos.return.post.*` / `pos.exchange.post.*` は開発者プレビューで、今は deploy できない。返品・交換の後の画面を前提にした設計にしない。
- 重ね表示の `s-modal` は、画面に置いて `command="--show"` / `commandFor` で開く。確認は画面ごと切り替えるほうが確か（3章）。

防ぐ仕組み: pos-receipt は試験 `scripts/lib/posExtensionComponents.test.mjs` で、`extensions/` に POS に無いタグが入ると失敗するようにしています（使えるタグの一覧と ui-extensions の版も固定）。ほかのアプリも同じ試験を写して使えます。テストしたい計算は `.jsx` ではなく `extensions/common/*.js` に置くと、試験から読み込めます。

## 8. 管理画面との分担

POS には店の人がその場で使うものだけを置き、挙動の切り替えは管理画面に置きます。

- 店や会社によって変わる挙動（例: 会計をやり直すときにカートに入れるか下書きを作るか、返金の予約を使うか）は、コードに固定せず管理画面で設定できるようにする。POS はその設定を読んで、使わないボタンを出さない。
- 開発者向けの項目は、自社用（カスタム）アプリでは「詳しい設定」に畳み、公開アプリでは出さない。
- 管理画面の作りは「管理画面の UI ルール（完全版 v1.1）」に従う。

## 9. 確認項目（PR を出す前に）

POS の画面を作る・直す PR では、次を確かめて PR 本文に書きます。

- [ ] 左下に「戻る」（完了画面は「閉じる」）、右下に主ボタン 1 つの固定フッターがある
- [ ] 入口（タイル）ごとに見出し 1 つ・ボタン 1 つで、別の機能が混ざっていない
- [ ] 一覧は 2章の並び（上固定・区切り線・等分の絞り込み・0 件のときの「すべて表示する」）
